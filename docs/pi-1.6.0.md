# Pi 1.6.0 compatibility and validation

Target: **`@earendil-works/pi-coding-agent@1.6.0`** (released 2026-11-20) with the matching `pi-ai`, `pi-agent-core`, `pi-tui`, `pi-mcp`, `pi-codemode`, `pi-telemetry` and `pi-schema` 1.6.0 packages. Sources: the [v1.6.0](https://github.com/earendil-works/pi/releases/tag/v1.6.0) release (same text as the installed package's `CHANGELOG.md`), the `pi-mcp`/`pi-schema` changelogs, and the public declarations (`index.d.ts`, `core/extensions/types.d.ts`, `core/agent-session*.d.ts`, `core/exec.d.ts`, `core/tools/*.d.ts`, pi-ai, pi-agent-core, pi-tui) and the Codex Responses/find implementations compared with 1.5.2. The earlier record is [Pi 1.5.2](pi-1.5.2.md).

## What changed in Pi and what it means here

| Pi 1.6.0 change (upstream) | Effect on this repository |
|---|---|
| **Breaking:** `Component.render()` returns `readonly string[]`; `Container` (and other pi-tui/Pi components such as `Image`, `Text`, `Markdown`, `Box`) may return the same cached array across frames, so output must be copied before it is changed (#9549). | images was the only package that returned another component's output from its own `render()`: `src/cell-preview.ts` `CellImage` (the fallback component), `src/paste.ts` `MarkedOrCells` (the native `Image` or the cells) and the `Image.prototype.render` wrapper in `src/terminal-refs.ts` (marker provider and its per-image cache). They failed images' typecheck on 1.6.0 (TS4104) and now declare `readonly string[]` (`MarkerProvider`, `Rendered`); none of them modified the lines (`addMarkers` already copies), and the marker cache still compares array identity, which now hits more often. orche's `src/extension/render.ts` and Workbench's `lib/runtime.js` build new arrays per call and never touch another component's output; no package subclasses `Container`. |
| The `openai-codex` provider sends the system prompt as a leading `developer` item of `input` instead of top-level `instructions` (#12273), and serializes `maxTokens` as `max_output_tokens` ("ignoring a model's maxTokens" fix; Pi's default is the model's `maxTokens` fitted to the context, unless `compat.supportsMaxOutputTokens` is false). | orche's `test/pi/output-cap.test.ts` "the real Codex Responses request body of a compaction …" drives pi-ai's real Codex body builder; it pinned the 1.5.x wire (`instructions`, no `max_output_tokens` with the cap off) and failed. It now checks the summarization prompt in the leading developer item and that the bodies carry no `instructions`; every body carries Pi's own 128000. orche's `src/pi/output-cap.ts` keeps a `max_output_tokens` the request already has (its rule 1), so on this wire its decision is now `payload` and **`outputCap.tokens`/`outputCap.models` no longer replace Pi's value** (the test covers auto, off and `tokens: 64000`); the module comment says so. Scope: only `cliproxyapi-codex-responses` Claude models (the former `@router-for-me` provider); the bundled `pi-cliproxyapi-provider` serves Claude on Anthropic Messages, where orche's cap was already out of scope. Production code is unchanged; whether orche's configured budgets should override Pi's default there is left to the maintainer. |
| `find` path patterns are relative to the search directory (`src/*.ts` no longer matches `pkg/src/a.ts`), `./` prefixes work (#12066, #12020); the parameter description says so. | Only Pi's own fd matching changed. orche's `src/tools/find.ts` supplies its own `FindOperations.glob`, which already matched path patterns against the path relative to the search root (and strips `./`); orche's tool now also shows Pi's new, matching description. Tests `find-gitignore`, `prepare-arguments` pass. |
| `AgentSession.reload()` emits `session_start` again when the SDK host bound extensions with `bindExtensions({})`. | orche's worker sessions bind capability extensions with `bindExtensions({})` (`src/pi/session-factory.ts` `bindFactoryExtensions`) and reload once in `enableTaskWorkflow`; on 1.6.0 the capability extensions (MCP, codegraph, …) start again after that reload instead of staying stopped. Suites pass; no change. |
| `pi.exec` reports 128 + signal (143 SIGTERM, 137 SIGKILL) instead of 0 for a command ended by a signal. | codegraph (`src/index.ts`: `--version`, `sync`, `status`) treats only `code === 0` as success, so a timed-out or aborted run is now reported as a failure, as intended. No other package uses `pi.exec`. |
| MCP tools loaded by `tool_search` are no longer dropped on resume/`/reload` when an extension deactivates only its own tool at `session_start` (#11996). | browser's `src/extension/index.ts` already preserves other extensions' pending tools when it calls `setActiveTools`; the root `scripts/mcp-lifecycle.test.mjs` (browser/physical-desktop/codegraph with real MCP, reload and resume) passes on 1.6.0. |
| Errors thrown by `pi.events` handlers are reported as extension errors; RPC `new_session`/`switch_session`/`fork`/`clone` run `session_start` once (previously twice); diagnostics after a session replacement are shown (`AgentSessionRuntime.takeUnreportedDiagnostics()` new); package install output is captured in interactive mode (`PackageCommandOutput`, `packageCommandOutput`). | browser, orche and session-bus use `pi.events`; their handlers are unchanged and now surface through Pi's error path instead of `console.error`. session-bus starts its endpoint at `session_start` in `tui`/`rpc` mode and now gets one start per replacement. No package hosts an `AgentSessionRuntime` or installs packages itself (orche uses `DefaultPackageManager.getInstalledPath()` only). Not affected. |
| Read results keep no stale "model does not support images" note (`ReadToolDetails.imageUnsupportedByModel`); cancelling `read` while opening no longer exits; Esc during a tool batch gives unstarted calls "Operation aborted" results; `runToolCall` checks an aborted signal first; bash output ending in a >100KB line is shown. | orche wraps Pi's `read` (`src/tools/read.ts`) without its own operations and passes images through; its read/bash/abort suites pass. Not affected. |
| Removed from the declarations: `resolveModelScope`, `restoreModelFromSession` (model-resolver), pi-ai `mapStopReasonString`, `ConvertResponsesMessagesOptions.includeSystemPrompt`; `utils/deprecation` gone. | None is used by these packages (only historical `orche/results/` artifacts of the former CLIProxyAPI provider mention `includeSystemPrompt`). |
| GPT-6.2 Astra/Sol (new default on `openai`, `azure`, `openai-codex`), Qwen Token Plan gateways/models, `undici` 8.12.4, Anthropic message threads for any api.anthropic.com provider, OpenAI non-strict tools for schemas with an untyped node, Mistral strict tools, non-OpenAI OpenAI-compatible providers get `system` role messages, retries on `Connection closed.`/socket error codes, llama.cpp default port 9931, TUI image/overlay/scrolling/suspend fixes, `pi-mcp` `mcpServerSummary`. | Requests go through Pi's own provider code; no package sets these options or depends on the old defaults. CLIProxyAPI's Chat Completions models (non-GPT, non-Claude) now receive `system` instead of `developer` messages from Pi; its offline tests pass, live behaviour is not verified. |

## Changes

- The eight TypeScript packages pin their Pi **development** dependencies and locks to 1.6.0 (`pi-commit`: `bun.lock`). `package.json` files keep their formatting (only the version strings change). With them the locks move pi-ai 1.6.0's pinned dependencies `@google/genai` 2.21.0 → 2.32.0, `openai` 7.19.0 → 7.59.0, `undici` 8.12.3 → 8.12.4 and `ws` 8.22.0 → 8.23.0; in `codegraph` npm also re-resolved some transitive AWS SDK/Smithy packages within their ranges. CLIProxyAPI's lock was updated with `--legacy-peer-deps` as before; its `pi-cliproxyapi-provider` stays at the locked 0.16.18 (the local install was 0.16.13 before the reinstall). Host-provided `*` peers and runtime dependencies are unchanged. Not pinned (no Pi development dependency, none added): `pi-workbench`, `pi-skillcache`, `pi-tmp`, `pi-eval-loop` and the root manifest.
- Gates: `scripts/pi-harness.mjs`, `scripts/pi-versions.mjs`, `scripts/pi-compat.mjs`, `scripts/verify-install.mjs` and `pi-workbench/tests/pi-host.mjs` default to 1.6.0.
- Code: images `src/cell-preview.ts`, `src/paste.ts`, `src/terminal-refs.ts` (read-only render output, above); orche `src/pi/output-cap.ts` (module comment only).
- Tests: orche `test/pi/output-cap.test.ts` as described above.
- Docs: root README, `browser/README.md`, `cliproxyapi/README.md` (Pi 1.6.0 and the locked provider 0.16.18).
- `orche/CHANGELOG.md` is not edited: it carries uncommitted, unrelated work, and the 1.5.0/1.5.2 migrations did not add orche entries either; this record and the root `CHANGELOG.md` describe the orche changes.

## Reproduce the checks

Same as [1.4.0](pi-1.4.0.md#reproduce-the-checks) with a 1.6.0 package directory:

```sh
export OMP_PI_DIR=/path/to/node_modules/@earendil-works/pi-coding-agent   # 1.6.0, with pi-ai/pi-tui 1.6.0 beside it
export OMP_PI_VERSION=1.6.0
export OMP_COMPAT_LOG_DIR=/path/to/scratch/pi160-results
npm run test:compat      # 22 commands
OMP_INSTALL_NPM_CACHE=/path/to/populated/npm-cache OMP_INSTALL_TEST_DIR=/path/to/scratch npm run test:install
```

The notes of [1.5.0](pi-1.5.0.md#reproduce-the-checks) on filling the offline npm cache for `test:install` and on scratch path length (pi-gui's `test/portal-activation.test.ts` binds a D-Bus socket under `TMPDIR`) still apply.
